2. Engineering principles and SOLID interpretation
SOLID aplikohet ne kufijte e sistemit dhe ne drejtimin e dependencies, jo si ceremonial abstraction. Qellimi eshte qe biznes rules te testohen pa rrjet, pa Supabase, pa Meta dhe pa OpenAI.
Parimi
Rregulli praktik ne kete sistem
Single Responsibility
Module dhe application service kane nje arsye biznesi per te ndryshuar. Publishing nuk gjeneron content; Billing nuk di Meta API.
Open/Closed
Provider adapters implementojne ports; nje provider i ri shtohet pa ndryshuar domain service.
Liskov
Adapters respektojne contract semantics, error taxonomy dhe idempotency; nuk fshehin limitations.
Interface Segregation
Ports te vogla: SocialPublisher, SocialReader, AiTextGenerator, ImageEditor, BillingGateway, NotificationSender.
Dependency Inversion
Domain/Application varen nga interfaces; Infrastructure varet nga domain contracts.

2.1 Additional non-negotiable rules
Make invalid states hard to represent: status transitions kalojne vetem permes domain policy/service.
No provider SDK objects cross the adapter boundary; mapohen ne internal DTO/value objects.
No package-name conditionals ne feature code. Gjithcka kontrollohet nga EntitlementService.
No raw model names ne domain code. Perdoret capability routing: fast_text, quality_text, premium_reasoning, image_edit.
No irreversible DB migration ne te njejtin deployment me kodin qe e kerkon; perdoret expand -> backfill -> switch -> contract.
No background side effect pa idempotency key, retry policy dhe observable attempt record.
No AI-generated commercial fact pa evidence reference ose explicit user input.
No production-only behavior qe nuk mund te testohet ne staging me provider sandbox/test account.

4.1 Signup to first draft

Sistemi importon metadata/post history ne background; progresi shfaqet ne UI dhe eshte resumable.
Business Brain gjeneron candidate facts dhe brand voice. User i konfirmon faktet komerciale/sensitive.
User ngarkon real assets; sistemi krijon variants/metadata dhe i ben searchable.
AI krijon draftin e pare nga verified evidence pack. Drafti nuk publikohet pa approval ne default policy.
4.2 Scheduled publication
Marketer zgjedh immutable content version dhe target social accounts.
Approver ose policy engine e kalon versionin ne APPROVED.
Schedule ruhet ne UTC, por paraqitet ne brand timezone; DST edge cases testohen.
Due dispatcher ben enqueue idempotent te publication job; queue consumer merr lock/visibility timeout.
Publisher verifikon entitlement, token/account health, version status dhe duplicate guard para remote call.
Attempt ruan request fingerprint dhe provider external id; pas timeout sistemi reconcile-on-read para retry.
Final result kalon ne PUBLISHED ose explicit retryable/terminal failure; user njoftohet kur duhet.
4.3 Disconnect / revoke
Disconnect ndalon jobs te reja per account, invalidon local token reference, shenon connection REVOKED/DISCONNECTED, ruan historikun e posts/analytics sipas retention policy dhe nuk fshin data pa explicit deletion request. Scheduled jobs qe varen nga account kalojne ne BLOCKED dhe kerkojne reconnect ose retarget.

7. Data architecture and multi-tenant persistence
7.1 Database conventions
Primary keys UUID; every tenant resource contains organization_id; brand-scoped resources additionally contain brand_id.
All timestamps are timestamptz in UTC; brand timezone is an IANA timezone string and only affects display/scheduling input.
Money stored as integer minor units + ISO currency; never floating point.
JSONB limited to provider payload snapshots, extensible metadata and AI diagnostics; core business fields stay typed columns.
Every mutable aggregate has created_at, updated_at and optional version integer for optimistic concurrency.
Soft delete only where product semantics require recoverability; privacy deletion uses explicit purge workflows, not endless soft-delete.
Foreign keys are explicit. Cascades are used only when ownership is unambiguous; security/audit records use restricted deletion rules.
Indexes follow measured query paths: (organization_id, brand_id, status), scheduled_at partial indexes, provider external ids unique per account, created_at cursor indexes.
7.2 RLS strategy
RLS eshte aktiv per tenant tables. API runtime perdor DB role pa BYPASSRLS. Pas JWT + membership authorization, transaction vendos SET LOCAL app.user_id dhe app.organization_id; policies lejojne rows vetem kur organization_id perputhet me tenant context. Worker runtime perdor role te vecante dhe vendos organization context nga job i verifikuar. Migration/admin role nuk perdoret nga request path.
Test requirement
Cdo migration qe shton tenant table deshton ne CI nese tabela nuk ka organization_id kur kerkohet, RLS enabled, policy tests dhe negative cross-tenant test. Kjo eshte release gate, jo checklist manual.

7.3 Transactional consistency
State change dhe event/outbox row shkruhen ne te njejtin DB transaction. Worker side effects nuk nisen direkt nga HTTP handler. Ky pattern eliminon rastin ku DB commiton por enqueue/publish humbet, dhe mundeson replay te kontrolluar.
8. Authentication, secrets and application security
8.1 Authentication
Supabase Auth eshte identity provider. API verifikon signature, issuer, audience, expiry dhe key rotation nga JWKS.
Email verification kerkohet para external integrations. MFA architecture eshte e gatshme; Owner/billing/destructive actions mund te kerkojne step-up authentication.
Session/token handling ndjek Supabase supported flow; asnje token autentikimi nuk log-ohet.
Account lock/rate limits/bot protection konfigurohen sipas production checklist dhe risk profile.
8.2 Social credentials
Meta access tokens nuk ruhen plaintext ne application tables. Ruhet credential reference + encrypted ciphertext me envelope encryption; master key jashte DB ne managed secret/KMS. Metadata jo-sekrete perfshin provider, scopes, issued_at, expires_at, last_validated_at dhe token_version. Rotation dhe revoke trajtohen si first-class flows.
8.3 Web security baseline
Kontrolli
Implementation requirement
Transport
HTTPS only; HSTS after domain validation; secure TLS defaults; provider callbacks only HTTPS.
Browser
CSP, frame-ancestors, nosniff, Referrer-Policy, secure/samesite cookies when cookies are used.
CSRF
State-changing cookie-auth endpoints require CSRF defense; bearer endpoints avoid ambient authorization.
CORS

9. Meta integration architecture
9.1 Connection model
SocialConnection perfaqeson OAuth grant/credential relationship; SocialAccount perfaqeson nje Facebook Page ose Instagram Professional account. Nje connection mund te zbuloje disa accounts. UI nuk supozon capability uniforme: adapter kthen capability matrix per READ_PROFILE, READ_MEDIA, READ_INSIGHTS, PUBLISH_IMAGE, PUBLISH_CAROUSEL, PUBLISH_REEL etj.
9.2 OAuth and webhook rules
OAuth initiation gjeneron cryptographically-random state dhe server-side pending record me expiry; PKCE perdoret ku provider flow e mbeshtet.
Callback validohet nje here; code exchange behet server-side; token encrypted immediately; browser merr vetem result status.
Scopes ruhen dhe krahasohen me required capability. Missing scope shfaqet si degraded connection, jo generic failure.
Webhook challenge/signature verifikohet; raw event fingerprint ruhet per deduplication; processing behet async.
Provider error codes mapohen ne internal taxonomy: AUTH_REVOKED, RATE_LIMITED, TEMPORARY, VALIDATION, PERMISSION, MEDIA_FETCH, UNKNOWN.
API version pinning konfigurohet ne adapter dhe upgrade-ohet me contract tests, jo implicit latest.
9.3 Import and sync
Initial sync importon vetem data qe permissions/API e lejojne. Cursor/checkpoint ruhet per account. Re-sync eshte incremental, resumable dhe idempotent; external object unique key eshte (provider, social_account_id, external_id). Raw provider payload mund te ruhet me retention te shkurter per debugging, ndersa normalized fields ruhen per produkt.
9.4 Publishing constraints
Media final qendron private. Vetem gjate provider fetch krijohet short-lived signed/publicly-accessible URL me TTL minimal. Publisher nuk supozon se remote call failure do te thote no post: ne timeout/ambiguous outcome, ben reconciliation para retry per te shmangur duplicate post.

17. API contract and error model
17.1 HTTP standards
Public application API versioned under /api/v1. Breaking changes require /v2 or compatibility window.
OpenAPI is generated from FastAPI and CI generates typed TypeScript client; drift between committed client and API fails CI.
Cursor pagination for feeds/history; offset pagination only for small admin tables.
Resource mutation uses optimistic concurrency where concurrent edit is plausible (version/If-Match equivalent).
Idempotency-Key required/supported on create payment, generation request, schedule and other replay-prone commands.
request_id and trace_id returned in errors for support; no stack traces or provider secrets to client.
17.2 Error envelope
Problem {  type: "https://docs.example.com/problems/<code>",  title: string,  status: int,  code: "CONTENT_NOT_APPROVED" | "META_RECONNECT_REQUIRED" | ...,  detail: safe string,  request_id: string,  field_errors?: [{ field, code, message }]}
API errors mapohen nga domain/provider errors ne stable internal codes. Frontend nuk parse-on provider text. Error taxonomy dokumentohet dhe perdoret nga support runbooks.
18. Async processing, outbox and event contracts
18.1 Why durable asynchronous work
AI, image processing, social sync dhe publishing jane remote/slow/failure-prone. HTTP request duhet vetem te validoje command-in, te ruaje intent-in dhe te enqueue durable work. UI merr job/resource status dhe mund te perdore polling/realtime notification si optimization.
18.2 Outbox pattern
Application transaction muton aggregate dhe shton outbox_event me unique event_id.
Dispatcher lexon unsent events dhe i dergon ne queue me idempotency key.
Consumer ruan processed marker/result sipas job type dhe kryen side effect.
Pas suksesit message archived/deleted; pas transient failure visibility timeout/backoff e ben available perseri.
Poison messages kalojne terminal/ops flow pas bounded attempts; nuk retry-hen pafund.
18.3 Event compatibility
Event payload ka schema_version. Consumers duhet te tolerojne additive fields. Breaking event changes krijojne version te ri dhe dual-publish/dual-read gjate migration window. Event payload nuk permban social access tokens ose raw secrets.

Appendix D - Coding and review standards
D.1 Python/FastAPI
Python 3.14 stable; pyproject.toml + locked dependencies; ruff; strict-enough static typing policy; pytest.
Pydantic request/response DTOs at transport boundary; domain entities are not HTTP schemas.
Async only when I/O path benefits and driver is async; no fake async around CPU-heavy image work.
Repository transaction boundaries explicit; no implicit commit inside low-level repository method.
No broad except Exception without rethrow/mapping/telemetry; provider errors normalized at adapter boundary.
Time comes from injected Clock in domain-sensitive tests; IDs/idempotency injectable where determinism matters.
D.2 Nuxt/TypeScript
Nuxt 4, TypeScript strict; API types from generated client; no hand-copied backend DTOs.
Server/client boundary explicit; secrets never in public runtime config; SSR-safe composables.
Pinia only for genuine cross-route client state; server state comes from typed query/composable pattern, not duplicated global store.
Every primary screen implements loading, empty, error, forbidden/degraded states and responsive behavior.
Accessibility baseline: semantic controls, keyboard paths, labels, focus, contrast, reduced-motion respect where relevant.
No business authorization encoded only in route middleware; server remains authoritative.
D.3 SQL and migrations
Migration filename/order deterministic; every table has owner/context documented in migration comment or schema docs.
Constraints enforce invariants that are truly data-level: uniqueness, FK, status check where stable, nonnegative usage.
Index additions justified by query; unused/duplicate indexes reviewed after telemetry.
Backfills resumable/batched for large tables; no table rewrite during peak without plan.
RLS policy tests live beside migration tests and include allow + deny cases.

47. Frontend state, data fetching and reliability
Use Nuxt useFetch/useAsyncData or a single approved query abstraction consistently; do not mix ad-hoc fetch clients.
Generated TypeScript API contracts are the network boundary. Runtime validation is required for provider-originated/untrusted payloads where appropriate.
Mutations use disabled/in-flight state and idempotency keys for commands that can duplicate server side effects.
Autosave uses debounce + version/ETag semantics; conflict returns explicit UI, not silent last-write-wins for important content.
Optimistic UI is allowed only when rollback is deterministic and server result cannot cause external side effect confusion.
Route transitions preserve unsaved drafts or block navigation with an explicit decision.
Offline/intermittent mode keeps local unsent draft only for low-risk authoring; publish/schedule always needs confirmed server state.
